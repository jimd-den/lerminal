==================================================
PRODUCT DEFINITION
==================================================

GRIOT is not a chatbot, productivity dashboard, online course platform, or generic notes app.

GRIOT is a learning shell.

A user may begin with:
- A note.
- A question.
- A pasted excerpt.
- A URL.
- A source document.
- A project idea.
- A goal they cannot yet articulate clearly.

The system helps them progressively turn material into:
- Questions.
- Concepts.
- Evidence.
- Claims.
- Prerequisites.
- Experiments.
- Tasks.
- Deliverables.
- Recall practice.
- A visible proof trail.

The user should not need to understand commands, agent scopes, research provenance, FSRS, pipelines, or semantic roles on day one.

Those capabilities must remain fully available and discoverable as the user gains confidence.

The UI must use progressive disclosure:
- Beginner surface: capture, understand, practice, make progress.
- Intermediate surface: sources, prerequisites, experiments, status gaps, study generation.
- Advanced surface: card selection, explicit pipelines, custom commands, custom assistants, prompt editing, assistant profiles, receipts, provenance, typed command expressions.

The app’s deepest promise is trust:
- The user can always inspect where an output came from.
- The app distinguishes user-provided material, deterministic app findings, agent hypotheses, and real web evidence.
- AI never falsely claims it searched, read, extracted, cited, or completed an action.
- Search is executed only by SearchGateway.
- Extraction is executed only by ExtractionGateway.
- Model use is always visible before and after execution.
- No network/model action occurs without an explicit, readable preflight.
- Errors are specific and actionable.
- A failed model or web operation is never replaced by fake success.

==================================================
FOUNDATIONAL INTERACTION MODEL
==================================================

Preserve and make visible the Unix model:

- Cards are universal material.
- Selected cards are stdin.
- Commands are transformations.
- Result cards are stdout.
- Groups are folders/scopes.
- Pipelines compose transformations.
- Operation receipts are history.
- Provenance is inspectable lineage.
- Agent profiles are named, editable tools—not hidden personalities.
- Web research is an external operation, never implied by generic “Ask.”
- The canvas is the primary home surface.

However, do not make the user type terminal commands by default.

Mobile adaptation:
- Touch-first action tiles are precomposed commands.
- A touch action always maps to a real command or request object.
- The user can reveal the underlying command/pipeline expression.
- Typing is a power-user path, never required for normal use.
- Selection creates an explicit visible input bundle.
- The visible actions change based on selected card roles and state.
- Every action has large, stable touch targets.
- The bottom thumb zone is reserved for the highest-frequency actions.
- Avoid menus inside menus and icon-only critical controls.

Core product rule:
“Touch is the friendly syntax. Pipelines are the underlying truth.”

==================================================
FIRST-RUN EXPERIENCE
==================================================

A new user must not see a blank terminal, a complex dashboard, or an API-key wall.

First-run sequence:

1. Welcome:
   - Plain statement:
     “Capture something you want to understand, make, or solve.”
   - Options:
     - Start with a thought.
     - Paste a source.
     - Define a goal.
     - Explore a blank workspace.
   - Explain in one sentence that GRIOT turns notes into questions, evidence, practice, and projects over time.

2. First capture:
   - Support quick note, question, URL/source, pasted text, and project idea.
   - Explain where the item was saved.
   - Show only 2–3 contextual next actions.
   - Do not show every available power tool.

3. First next action:
   - For a note:
     - Explain this.
     - Find prerequisites.
     - Attach to a goal.
   - For a source:
     - Extract key ideas.
     - Assess source.
     - Make practice questions.
   - For a question:
     - Research it.
     - Turn it into an experiment.
     - Add supporting notes.
   - For an experiment:
     - Add measurement.
     - Find prerequisites.
     - Create a next task.

4. Goal architect:
   - Keep existing goal architect design and implementation direction.
   - It must remain a focused bottom sheet or contained flow, never a permanent general chat screen.
   - Ask one high-leverage question at a time.
   - Show rationale for the question.
   - Preserve skipped answers.
   - Build a transparent working map.
   - Label model contribution “Agent hypothesis — verify or edit.”
   - Allow fully manual use without an API key.
   - Offer web research only after explicit opt-in.
   - Create mission cards only after the user approves a clearly labeled draft.

==================================================
FIELD: MAIN CANVAS
==================================================

FIELD is the primary home and replaces the feeling of a generic list of notes.

It must still use the existing card and group model. Do not build a separate graph database or duplicate source of truth.

FIELD presents a bounded, scrollable working set:
- Current group / workspace context.
- Mission module only when a mission exists.
- Current next action.
- Notes, questions, sources, concepts, claims, experiments, tasks, and results represented as cards.
- Cards remain the actual domain cards.
- Filters are presentation state, not destructive reclassification.

Card visual grammar:
- Semantic role label.
- Title.
- Concise preview.
- Relevant status only: due, source retained, evidence caution, agent-generated, selected, incomplete, blocked.
- Provenance affordance when provenance exists.
- One primary contextual action available on expansion.
- Selection affordance is always visible and accessible.
- Cards must remain easy to scan one-handed.

Card roles:
- Note: user capture or working thought.
- Source: imported/pasted/retained source.
- Chunk: readable extracted learning material.
- Question: unresolved or recall prompt.
- Concept: a structured explanation/idea.
- Claim: a proposition supported or needing support.
- Experiment: hypothesis, method, measure, result, next action.
- Task: a concrete action.
- Deliverable: output that demonstrates capability.
- Group: scope/container/document/milestone.
- Goal: workspace mission.

Mission module:
- Only shown for workspaces with a mission.
- Display:
  - Goal title.
  - Target deliverable.
  - One success criterion.
  - Counts: blockers, prerequisites, evidence, next tasks.
  - One recommended next action with a short deterministic reason.
- Tapping it opens the status gap report.
- Never show an opaque “percent complete.”
- If any maturity indicator exists, it must state that it is heuristic and explain why.

Status gap report:
- Answer:
  - What do I want?
  - What do I have?
  - What is missing?
  - What should I do next?
- Use deterministic card graph analysis before any model enrichment.
- Clearly distinguish:
  - Deterministic result.
  - Agent hypothesis.
  - Web-grounded evidence.
- Allow the user to turn a recommendation into a task, research preflight, experiment draft, or study action.

==================================================
AGENT SYSTEM
==================================================

Agents are user-configurable, scoped tools.

Do not use a single global “AI” assistant with a hidden prompt.

Build an Agent Studio with:
- Built-in agents.
- User-created agents.
- Session-only agents.
- Workspace-bound agents.
- Global saved agents.
- Duplicate built-in agent to customize.
- Export/import agent definition as JSON only if safe and compatible with existing storage patterns.

Required built-in agents:
1. Goal Architect:
   - Clarifies intention.
   - Builds working map.
   - Proposes mission draft.
   - May propose research queries.
   - Does not browse without approval.

2. Learning Coach:
   - Explains selected material.
   - Finds misconceptions.
   - Creates teaching explanations.
   - Generates questions only from available context.
   - Encourages prediction and application rather than long lectures.

3. Research Scout:
   - Proposes/refines research queries.
   - Classifies source needs.
   - Helps assess retained evidence.
   - Uses actual web results only after SearchGateway runs.
   - Never claims it searched unless a search receipt proves it.

4. Prerequisite Mapper:
   - Identifies missing concepts and dependencies.
   - Outputs explicit question/concept cards.
   - Marks uncertain suggestions as hypotheses.

5. Experiment Designer:
   - Converts an uncertainty into:
     - Hypothesis.
     - Method.
     - Required tools/materials.
     - Measurement.
     - Expected result.
     - Stop condition.
     - Next action.
   - Never claims an experiment was conducted.

6. Study Builder:
   - Converts selected learner-approved content into recall or cloze material.
   - Requires explicit confirmation before enrollment in FSRS/review.
   - Must preserve links to source content.

7. Capstone Planner:
   - Turns a mission and selected evidence into milestones, tasks, deliverables, and explicit unknowns.
   - Must avoid creating false certainty or arbitrary deadlines.

Agent definition model:
Create or extend a serializable domain model, preferably in entities, such as:

type AgentProfile = {
  id: string;
  name: string;
  description: string;
  scope: "builtin" | "global" | "workspace" | "session";
  systemPrompt: string;
  allowedCapabilities: AgentCapability[];
  defaultModelId?: string;
  preferredOutputRoles: SemanticRole[];
  contextPolicy: ContextPolicy;
  webPolicy: "never" | "preflight-required";
  outputPolicy: OutputPolicy;
  createdAt: number;
  updatedAt: number;
  isBuiltin: boolean;
  isEditable: boolean;
  sourceProfileId?: string;
};

type AgentCapability =
  | "explain"
  | "goal-architect"
  | "query-planning"
  | "research-synthesis"
  | "prerequisite-mapping"
  | "experiment-planning"
  | "study-generation"
  | "capstone-planning"
  | "custom";

type ContextPolicy = {
  defaultScope: "selected-only" | "bounded-workspace" | "mission-only";
  maxCards: number;
  maxCharacters: number;
  allowSources: boolean;
  allowMission: boolean;
  allowPriorOutputs: boolean;
};

type OutputPolicy = {
  allowCardCreation: boolean;
  allowedRoles: SemanticRole[];
  requireReviewBeforeSave: boolean;
  createGroupForOutputs: boolean;
};

Requirements:
- Built-ins are read-only.
- “Customize” duplicates a built-in agent into a user-owned profile.
- User edits never mutate built-ins.
- Every prompt is visible and editable in the agent editor.
- Explain the impact of each capability and policy in plain language.
- Validate prompt, name, capability, model selection, and context limits.
- Do not allow profiles to request unbounded workspace upload.
- Allow session-only changes that disappear after the session.
- Persist global and workspace-scoped profiles safely.
- Keep existing assistant profiles backwards compatible through migration/adapters.
- If a profile references a missing model, show an actionable fallback selector; never silently switch models.

Agent Studio UI:
- List agents by scope: Built-in, Workspace, My agents, Session.
- Each item displays:
  - Name.
  - What it does.
  - Web availability.
  - Default context policy.
  - Default model if assigned.
  - Editable / built-in state.
- Agent detail:
  - Purpose.
  - Prompt editor.
  - Allowed actions.
  - Context policy.
  - Web policy.
  - Output behavior.
  - Model selection.
  - Test with sample context only if test execution is truthfully scoped and clearly separate from saved actions.
- Prompt editor must not expose users to opaque raw system behavior only:
  - Provide a plain-language “Behavior” summary.
  - Provide the exact editable prompt.
  - Provide a “Prompt Architect” action that proposes a revised prompt but never overwrites without confirmation.
  - Show diff before applying a generated prompt revision.
  - Preserve version history or at minimum a recoverable previous version for the latest edit.
- Do not send prompts or cards to a model merely by opening the editor.

Prompt Architect:
- This is an optional agent-assisted tool for designing another agent profile.
- Inputs:
  - User goal.
  - Desired behavior.
  - Expected inputs.
  - Desired outputs.
  - Boundaries.
  - Tone.
  - Model/capabilities available.
- Output:
  - Proposed name.
  - Description.
  - System prompt.
  - Context policy.
  - Suggested output roles.
  - Suggested web policy.
  - Safety/quality rationale.
- Must open an AI preflight showing what will be sent.
- Must show a diff.
- Must require explicit save.
- Must store provenance that an agent designed/revised the profile, with model metadata.
- Must not grant web access or broad context automatically.

CUSTOM COMMAND SYSTEM
==================================================

Custom commands are first-class user tools, not a hidden advanced setting.

Preserve existing command definitions and pipeline behavior.

Create Command Workshop.

A custom command may be:
- Deterministic macro: a saved ordered pipeline of existing deterministic commands.
- Agent command: a named agent profile plus explicit input/output policy.
- Guided action: a preflight-backed shortcut that opens a known operation with defaults.
- Research command: an explicit research workflow shortcut that always requires web preflight.
- Hybrid pipeline: deterministic stages plus a declared agent stage and/or research stage.

Do not allow arbitrary hidden code execution.

Custom command definition model should include:
- id.
- name.
- aliases.
- plain-language label.
- description.
- kind.
- pipeline expression or stage list.
- agentProfileId when applicable.
- required input roles/count.
- allowed input scope.
- web use declaration.
- output roles.
- destination policy.
- whether preflight is mandatory.
- session/workspace/global scope.
- createdAt/updatedAt.
- version/source metadata.
- optional icon only if it remains accessible and not essential to meaning.

Command workshop UI:
- Start with templates:
  - Explain simply.
  - Challenge my reasoning.
  - Turn notes into a practice set.
  - Research and compare sources.
  - Design an experiment.
  - Build a capstone plan.
  - My custom pipeline.
- Command composer:
  - Name and plain language description.
  - Input requirements.
  - Stage builder with reorderable stages.
  - Context selector.
  - Agent selector if applicable.
  - Model selection if applicable.
  - Web disclosure if applicable.
  - Output card roles.
  - Destination.
  - Preflight preview.
  - Underlying pipeline expression.
- Every stage must display:
  - What it reads.
  - Whether it uses model/web.
  - What it creates.
  - Side effects.
- Command validation:
  - Detect empty commands.
  - Reject invalid stage combinations.
  - Reject non-existent agent profile.
  - Reject required-selection commands when no selection exists.
  - Reject web usage without explicit preflight.
  - Reject output role conflicts.
  - Reject pipeline stages that cannot consume the previous stage’s outputs, where type knowledge exists.
- Commands can be pinned to the Tool Deck.
- Commands can be duplicated and edited.
- Built-in commands remain available and cannot be corrupted by user edits.
- Existing typed command aliases must continue working.
- If custom command behavior cannot be fully inferred, describe exposure conservatively rather than claiming it is deterministic, AI-free, or web-free.

==================================================
PERSISTENCE AND MIGRATION
==================================================

All changes must be additive and backwards compatible.

Requirements:
- Old cards, workspaces, schedules, palettes, assistant profiles, custom commands, and settings must load without data loss.
- New fields resolve to safe defaults.
- Built-in agents are generated or versioned safely; do not persist mutable copies as authoritative built-ins.
- User agent profiles, command definitions, and appearance profiles are stored separately or through an existing compatible repository model.
- Storage parse failures surface as errors, never as empty data.
- Do not silently overwrite user preferences.
- Version migrations must be deterministic and tested.
- Workspace scoped agents/commands must not appear in unrelated workspaces.
- Session agents/commands must not persist after app restart.
- Deleting an agent used by a command must warn and require reassignment/delete of dependent commands.
- Deleting a font must fall back safely.

==================================================
ACCESSIBILITY AND QUALITY
==================================================

- Minimum 44x44pt touch targets for primary interactive controls.
- Respect screen-reader labels and roles.
- Do not rely on color alone.
- Support Dynamic Type/font scale.
- Support reduced motion.
- Support dark and light modes.
- Ensure keyboard behavior is correct on Android and iOS.
- Bottom sheets and text editors must avoid keyboard overlap.
- Support one-handed use on a standard phone.
- Use clear, non-technical language by default.
- Show advanced terminology in inspectable detail views, not as required vocabulary.
