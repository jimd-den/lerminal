You are working in the Learnimal repository.

Build a new first-run and “Create Goal” experience called GOAL ARCHITECT.

PRODUCT INTENT

Learnimal is a mobile learning console, not a generic AI chat app. Its core model must remain intact:

- Cards are the universal stream.
- Selection is stdin.
- New cards are stdout.
- Commands compose.
- The agent is a visible, inspectable pipeline stage—not an invisible authority.
- The canvas remains the home surface.
- Users bring their own OpenRouter model and API key.
- The app must never imply that a model researched, read, extracted, or completed work that did not actually happen.

The experience should feel like a clean Normandy-style mission workstation:
calm, capable, information-rich, mobile-first, and focused. Do not imitate copyrighted UI assets or exact franchise visuals. Use the design principles: restrained panels, strong hierarchy, meaningful system labels, contextual status, and deliberate controls.

Do not turn it into a gamified dashboard, a chatbot product, or an opaque “AI planner.”

CORE OUTCOME

A new user should be able to open the app, describe an ambition, and work with a conversational goal architect to turn it into an achievable, evidence-aware learning mission.

The agent should help the user:
1. Clarify the desired outcome.
2. Define why it matters and constraints.
3. Understand the user’s intended approach.
4. Identify deliverables, milestones, and a meaningful first proof.
5. Surface likely prerequisite knowledge, tools, risks, and unknowns.
6. Optionally research comparable projects, official documentation, examples, and learning resources through the real SearchGateway.
7. Ask a small number of high-leverage follow-up questions.
8. Create an inspectable mission plan only after the user approves it.
9. Leave the user on the canvas with useful output cards and an obvious next action.

The goal is education that reaches beyond a conventional master’s-level experience:
active, project-grounded, evidence-aware, adaptive, and capable of helping the user produce real work. Do not make unsupported claims about educational efficacy. Make the sophistication visible through better scaffolding, real practice, source evaluation, experiments, feedback loops, and explicitly stated assumptions.

DESIGN SYSTEM: NORMANDY CONCEPT

Create an optional appearance profile named “Mission Console.”

It must be customizable through safe semantic controls:
- Theme mode: dark / light / system.
- Accent color: preset semantic-safe palette plus optional controlled custom accent.
- Surface tint: neutral / blue-black / graphite / deep teal.
- Google Font family: use the existing font installation flow by family name.
- Body font and mono font should remain separate roles.
- Font scale / density: compact / comfortable.
- Reduced motion: respect OS setting and existing app behavior.

Do not let custom color selection destroy semantics:
- Warning, error, web evidence, selection, and success must remain distinguishable.
- Accent color is for focus, primary actions, and neutral active state; it must not redefine destructive or caution states.
- Preserve accessible contrast.
- Maintain existing palettes and appearance settings as backwards compatible.

Typography:
- Use the selected Google font for readable body/headline text.
- Keep a system or monospace stack for commands, IDs, labels, timestamps, and structured metadata.
- Never use mono as default long-form reading text.
- Make touch targets large and clearly labeled.

Visual direction:
- App shell has a compact mission header.
- Panels are calm, low-ornament, and layered with subtle borders.
- Use structured labels sparingly: MISSION, CONTEXT, WEB EVIDENCE, BLOCKER, NEXT ACTION, OUTPUT, RUN COMPLETE, PROVENANCE.
- No fake telemetry, random percentages, radar, scanlines, coordinates, decorative crosshairs, or looping animation.
- Motion should only explain change, arrival, selection, or in-progress work. Respect reduced-motion settings.

GOAL ARCHITECT FLOW

Entry points:
- First launch with no workspace: begin Goal Architect.
- Existing user: add “Create goal” through Capture / workspace menu / command palette.
- Preserve the ability to create a blank workspace without agent assistance.
- If no API key exists, provide a deterministic manual goal setup path and clearly label what requires a model or web access.

The experience is a focused, card-like conversational sheet—not a permanent chat tab.

Stage 1 — Intent
Ask one question at a time, with a short explanation of why it matters.

Initial question:
“What do you want to be able to make, understand, or change?”

Then adaptively ask high-leverage questions such as:
- “What would count as a concrete finished result?”
- “Why does this matter to you right now?”
- “How do you currently imagine approaching it?”
- “What experience, tools, materials, or time do you already have?”
- “What constraints are real: deadline, budget, hardware, collaborators, or scope?”
- “What is the smallest proof that would show you are making progress?”
- “What part feels most uncertain or likely to block you?”

Do not rigidly ask every question. Ask only what materially reduces ambiguity.
Keep each turn concise. Let the user skip, edit prior answers, or answer by voice if voice input already exists.

Stage 2 — Quiet Assessment
As the user answers, create a transparent local assessment model. It should identify:
- Goal statement.
- Proposed deliverable.
- Constraints.
- Existing assets and prior knowledge.
- Assumptions.
- Open questions.
- Candidate prerequisites.
- Likely risks.
- Possible first experiment.
- Potential research queries.

This assessment is not a hidden model truth. Present it as:
“Working map — based on what you’ve told me.”

If a model is available, it may propose missing considerations, but label all such material:
“Agent hypothesis — verify or edit.”

Examples:
- “You mentioned WebGPU, but deployment/browser support is not yet specified.”
- “A playable vertical slice may need level-generation, performance profiling, input, and save-state decisions.”
- “You may want a frame-time budget before expanding content scope.”

Stage 3 — Optional Real Research Scan
After enough goal context exists, offer—not automatically execute—a clearly labeled action:

“Scan the web for comparable projects, official documentation, prerequisite topics, and possible constraints.”

The preflight must explicitly show:
- The exact search queries.
- Whether selected user answers or workspace context are included.
- The active model, if a model is used to generate/refine queries.
- That SearchGateway performs the actual search.
- That search results are candidates, not facts or endorsements.
- Where results will land.

The actual search flow must use the existing SearchGateway and research workflow.
Never let an LLM claim it searched when it did not.

Research results must remain inspectable:
- Title, domain, URL, snippet, query, access time.
- Relevance rationale.
- Evidence kind / source type when known.
- Cautions and limitations.
- Keep / Reject / Open / Extract controls.
- “Create cited brief” only from retained sources.
- Provenance for all saved source-derived cards.

Suggested source categories:
- Official specifications and documentation.
- Comparable open-source projects.
- Academic or technical papers when relevant.
- Tutorials, clearly labeled as tutorials rather than authority.
- Design / case-study references when appropriate.
- Tools, SDKs, frameworks, or hardware constraints.

Stage 4 — Mission Proposal
When sufficient information exists, create a reviewable mission proposal rather than silently writing a plan.

Show:
- Mission title.
- One-paragraph goal statement.
- Target deliverable.
- Success criteria.
- Constraints and explicit assumptions.
- Recommended first milestone.
- Smallest useful proof / prototype.
- Prerequisites to learn.
- Risks and unknowns.
- Recommended initial research or experiment.
- Suggested first cards to create.

Use a clear status:
“DRAFT MISSION — NOTHING HAS BEEN CREATED YET.”

Offer:
- Edit.
- Ask another question.
- Research gaps.
- Accept mission.
- Start blank instead.

On acceptance, create cards with semantic roles and provenance:
- One mission/workspace goal.
- A milestone or plan group.
- Prerequisite concept/question cards.
- Task cards for the first milestone.
- An experiment card when relevant, including hypothesis, method, measurement, expected result, and next action.
- Retained research sources only when the user chose to keep them.
- A “Mission assumptions” note.
- A “Known gaps” note.

Do not automatically enroll anything in spaced repetition.
Study-card generation remains an explicit later action.

Stage 5 — Mission Canvas
After acceptance, return the user to the normal one-canvas workspace.

Top of canvas:
- MISSION title and a one-line target deliverable.
- Three to four meaningful counters at most: blockers, prerequisites, evidence, next tasks.
- One “NEXT ACTION” recommendation with a reason.
- A tap target to open mission detail or status gap report.

Main canvas:
- Show created goal, task, experiment, source, concept, and question cards.
- Clearly distinguish card roles through semantic labels, not decorative color overload.
- Highlight newly created cards and explain they are selected only if selection actually changed.
- Preserve current card, grouping, command, capture, review, and pipeline behavior.

Bottom action dock:
Idle state:
- Capture
- Research
- Review
- More / Command

Selection state:
- Explain
- Research
- Connect
- Study
- More

The command palette remains a first-class interface:
- Keep typed pipelines.
- Keep existing commands and aliases.
- Add documented goal-related commands where appropriate:
  - goal
  - status
  - prereqs
  - experiment
  - build
- Each command must explain inputs, output, model/web exposure, and side effects.
- Goal Architect should be launchable from the command palette but must not replace pipelines.

AGENT BEHAVIOR

Create a dedicated GoalArchitect workflow and request/response model rather than hiding this inside generic ask.

The agent must:
- Ask purposeful questions, not produce a long lecture.
- Use the user’s answers as explicit context.
- State uncertainty.
- Separate user-provided facts, deterministic app findings, agent hypotheses, and web-grounded evidence.
- Propose concrete, testable milestones and experiments.
- Prefer scope reduction and early validation over aspirational over-planning.
- Challenge vague goals respectfully.
- Ask “where are we going next?” only when it is supported by the current mission state and available choices.
- Never silently ingest the whole workspace. Follow bounded context rules.
- Never browse without explicit user approval.
- Never claim a source was read, extracted, or cited unless the relevant gateway operation occurred and provenance exists.
- Never fabricate success after missing API keys, search errors, extraction errors, or model errors.

Use structured responses, e.g.:

type GoalArchitectTurn = {
  message: string;
  question?: {
    id: string;
    prompt: string;
    rationale: string;
    optional: boolean;
    choices?: string[];
  };
  workingMap: {
    goal?: string;
    deliverable?: string;
    constraints: string[];
    assumptions: string[];
    unknowns: string[];
    prerequisites: string[];
    risks: string[];
    candidateNextActions: string[];
  };
  recommendedResearch?: {
    query: string;
    rationale: string;
    sourceKinds: string[];
  }[];
};

Validate and normalize agent output before rendering it.
If model output is malformed, show an actionable failure state and preserve the user’s answers.

TRUST, RECEIPTS, AND UNDO

Every model or web operation must create an accurate receipt:
- Action name.
- Explicit scope.
- Input card IDs / answer IDs where applicable.
- Search queries actually executed.
- Whether web and/or model was used.
- Output card IDs.
- Destination.
- Model/profile metadata when applicable.
- Errors or partial success.
- Whether undo is available.

Support safe undo for cards created by mission acceptance or a goal-planning operation.
If cards were edited after creation, refuse undo safely and explain why.
Never report partial undo as complete success.
